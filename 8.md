# Client-Server-Architecture

Imagine you open Twitter on your phone.
You scroll your feed, like a post, write your own post, and comment on a post.

Ever wondered what's actually happening behind the scenes?

Your phone isn't the one doing all this work alone. It's talking to a powerful machine sitting in a data center somewhere.

This is Client-Server Architecture.

Client(app/browser) → Server

Client:
> usually a device like a phone or Browser
> sends requests and displays the response. 
> doesn't hold any business data or does any processing

Server:
> listens for requests, 
> processes them 
> sends back a response. 
> holds the business logic

How a request actually flows

-> Client sends a request ("get my feed") 
-> Server receives it 
-> Server processes it (runs logic, queries DB) 
-> Server sends back a response
-> Client renders it for the user

This is called a request-response cycle.

Why not just do everything on the client?

Devices differ in power, storage, and connectivity. You can't trust every device to store all your data or run heavy logic reliably.

Servers -> centralized and manage operations for all clients. 
Clients -> only work as end devices and focus on UX

Common variants

2-Tier
Client -> Server
Database resides in the same layer as the server

3-Tier
Client -> Application Server -> Database
 
*A server or application directly talking to the database is also considered 2-Tier architecture. For example, an application running inside your computer that reads/writes data on a file system on your computer 

Client-Server is the foundation on which almost every system is built, before Load Balancers, Caching, or Databases even enter the picture.
